You own your copy of the repository. Contributor permissions are separate from these maintenance responsibilities; see [Contributor scope](contributor-scope.md).

## Tiers

Upstream maintains platform code. The team maintains its content and settings. Generated files come from their declared sources. Starter examples are yours to adapt. These labels are guidance, not an automated merge policy.

## Path map

| Path | Responsibility |
| --- | --- |
| `src/platform/`, root build/configuration files, `.github/`, `.husky/`, `patches/`, shared `public/` assets | Supplied platform; review local changes during upgrades. |
| `src/systems/`, `src/modules/`, `src/prototypes/`, `contributors/`, `studio.config.json`, `README.md`, `AGENTS.team.md` | Team content and settings, including adapted starter examples. |
| `AGENTS.md`, managed skill adapters | Generated by `pnpm studio sync`; edit canonical sources. |
| `pnpm-lock.yaml` | Generated by pnpm from dependency manifests. |

## Updating a studio

Upgrades are manual Git work. There is no `studio update` command or special seed-preservation merge engine.

1. Preserve local changes in Git before starting. Use the existing `upstream` remote or add the official Design Studio repository when authorized. Fetch the chosen release tag, read its notes, and create an upgrade branch from the studio's current commit.
2. Inspect both the release diff and the proposed merge. Merge the exact tag using ordinary Git. Review **all** resulting content and configuration changes, including clean merges: Git does not know which sample files you customized or deleted. Preserve local prototypes, profiles, settings, systems, modules, and guidance deliberately.
3. Resolve conflicts on the upgrade branch. If intent is unclear, leave the conflict for review; `git merge --abort` cancels an in-progress merge. Do not join unrelated histories or discard local files to make a merge pass.
4. Reconcile dependency manifests and the lockfile, install dependencies, run `pnpm studio sync`, `pnpm test`, and `pnpm build`. Exercise the affected local workflows and permanent links. Run `pnpm test:release` when build, setup, or module lifecycle behavior changed.
5. Review the branch before merging it into the studio's working branch. Push only when requested. Upgrades do not publish the studio.

Keep upstream ancestry when cloning a release. For an unrelated-history installation, preserve its files and transfer owned work into a separate full clone for review.

## The installed release

Git history and release tags identify the source revision. `PLATFORM_VERSION` reports the code's version. Git records local integration changes.

## System roots

`src/platform/systems/` contains Studio's interface system; `src/systems/` contains prototype systems, including starter examples. The root constants and validation live in `src/platform/core/roots.ts`. IDs must be unique across roots.

## Module roots

Supplied modules live in `src/platform/modules/`; team modules live in `src/modules/`. Team modules and systems use the public `#studio/*` entries rather than platform internals; see [Modules and extensions](modules.md#public-api).

## Agent instructions

`pnpm studio sync` generates `AGENTS.md` from `src/platform/AGENTS.md`, enabled module routing, and `AGENTS.team.md`. It synchronizes managed adapters while preserving team-authored entries. Edit the sources, then sync; `--check` detects stale output.

## Mixed paths

Root `package.json` can contain team module dependencies alongside platform tooling. Systems keep their own manifests. Review dependency changes together before regenerating the lockfile.
